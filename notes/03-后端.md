# 三、后端：服务器上运行的

> 学习笔记分册 · 返回 [总目录](../学习笔记.md)

## 知识树

```
Node.js
├── JS 运行时（让 JS 脱离浏览器，在服务器上跑）
├── npm 是其包管理器
└── node app.js → 启动服务 → 监听端口 → 等待浏览器请求

Express（Web 框架）
├── 路由：URL ↔ 处理函数的对应表
├── 中间件：请求到达后、返回响应前，插入的处理逻辑（Session、表单解析等）
└── res.send() vs res.render()：返回纯文本 vs 渲染模板

一个请求的完整流转
浏览器 → routes（URL匹配）→ controllers（解析请求）→ services（业务逻辑）→ models（查数据库）→ 逐层返回 → 浏览器收到 HTML
```

## 模块分层（MVC）

| 目录 | 对应层 | 职责 |
|------|--------|------|
| `routes/` | 路由 | URL 和函数的对应表 |
| `controllers/` | Controller | 解析请求参数、调用 Service、返回响应 |
| `services/` | Service | 真正的业务规则和逻辑判断 |
| `models/` | Model / DAO | 和数据库打交道，执行 SQL |

## 数据库与 SQLite

```
数据库
├── 存储结构化的持久数据（用户信息、文章内容、评论）
├── 和 Session 的区别：Session 存临时登录状态，数据库存永久业务数据
├── SQLite：零安装，整个数据库就是一个 .db 文件
├── db.run()  → 写入（INSERT / UPDATE / DELETE）
├── db.get()  → 查一条
├── db.all()  → 查多条
└── ? 占位符 → 防 SQL 注入（用户恶意输入不会破坏 SQL 语句）
```

**SQL UPDATE / DELETE 写法**

```sql
-- UPDATE：修改已有行，SET 指定改哪些列，WHERE 指定改哪行
UPDATE posts SET title = ?, content = ?, updated_at = CURRENT_TIMESTAMP WHERE id = ?

-- DELETE：删除行，WHERE 指定删哪行。不加 WHERE 会删光整张表！
DELETE FROM posts WHERE id = ?
```

- `CURRENT_TIMESTAMP`：SQLite 内置函数，自动取当前时间，更新 `updated_at` 字段用
- `db.run()` 回调中的 `this.changes`：返回受影响的行数。改了 0 行 = 没匹配到数据（id 不存在）

**建表语句关键语法**

| 语法 | 含义 |
|------|------|
| `IF NOT EXISTS` | 表存在就跳过，不会重复建表导致报错 |
| `PRIMARY KEY AUTOINCREMENT` | id 自动递增，唯一标识每一行 |
| `UNIQUE` | 值不能重复（用户名、邮箱） |
| `FOREIGN KEY (user_id) REFERENCES users(id)` | 外键约束：文章的作者必须存在 |
| `module.exports = db` | 导出连接对象，其他文件 `require('./models/db')` 复用 |

## `{ user: req.session.user || null }` 解析

```javascript
// req.session.user  → 登录用户的 Session 数据，没登录时是 undefined
// A || B            → A 有值取 A，否则取 B
// null              → 明确的"空"，在 if 判断中同于 false
```

## 路由设计模式

**编辑功能的标准路由结构：**

```
GET  /posts/:id/edit  → 显示编辑表单（预填原有数据）
POST /posts/:id/edit  → 处理编辑提交（更新数据库）
```

两个路由都要做**三重校验**：
1. 登录检查（`if (!req.session.user)`）
2. 资源存在检查（`if (!post)` → 404）
3. 权限检查（`if (post.user_id !== req.session.user.id)` → 403）

GET 和 POST 都要做权限校验，不能只在 GET 做——攻击者可以绕过页面直接发 POST 请求。

**删除为什么用 POST 不用 GET？**
- GET 请求可被浏览器预加载、搜索引擎爬虫触发
- 如果 `/posts/3/delete` 是 GET，别人发一个 `<img src="/posts/3/delete">` 链接，你打开页面文章就被删了
- POST 需要主动提交表单，浏览器不会自动触发
- 同理：所有会改变服务器数据的操作（创建、修改、删除），都用 POST

## 评论功能

**comments 表设计：**

| 字段 | 类型 | 说明 |
|---|---|---|
| user_id | INTEGER | 谁评论的，外键 → users(id) |
| post_id | INTEGER | 评论哪篇文章，外键 → posts(id) |
| content | TEXT | 评论正文 |
| created_at | DATETIME | 评论时间 |

评论同时属于一个用户和一篇文章，所以有两个外键。查询时 `JOIN users` 拿评论者用户名，`WHERE post_id = ?` 限定某篇文章，`ORDER BY created_at ASC` 旧的在前。

**评论和文章路由的区别：**

| | 文章 | 评论 |
|---|---|---|
| 展示 | 独立页面 `/posts/:id` | 嵌入文章详情页 |
| 提交后 | 重定向到首页 | 重定向回文章详情页 |
| 路由数量 | GET + POST | 只需 POST |

评论没有独立的创建页面——表单直接嵌在 `post.ejs` 正文下方。

## 点赞功能

**likes 表设计：**

```sql
user_id INTEGER NOT NULL,
post_id INTEGER NOT NULL,
created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
UNIQUE(user_id, post_id)  -- 联合唯一约束：同一用户同一文章只能有一行
```

`UNIQUE(user_id, post_id)` 是联合唯一约束，从数据库层面保证一个人对一篇文章只能点赞一次。

**toggle 模式（点赞/取消二合一）：**

```
先 SELECT COUNT(*) WHERE user_id=? AND post_id=?
  → 已有记录：DELETE（取消点赞）
  → 没有记录：INSERT（点赞）
返回 { liked: bool, count: 当前总数 }
```

同一个接口处理点赞和取消，前端不用区分，后端判断即可。

**AJAX 点赞 vs 表单提交：**

| | 评论（表单提交） | 点赞（AJAX + fetch） |
|---|---|---|
| 提交方式 | `<form method="POST">` | `fetch()` in `<script>` |
| 页面行为 | 整页刷新（重定向） | 不刷新，只更新按钮 |
| 后端返回 | `res.redirect()` | `res.json({ liked, count })` |
| 用户体验 | 适合提交后需要看结果的场景 | 适合轻量交互，不打断阅读 |

AJAX 的核心：浏览器发请求 → 服务器返回 JSON → JS 更新 DOM，全程不刷新页面。

## `CREATE TABLE IF NOT EXISTS` 的使用边界

- **新增表**：直接用，重启服务即生效，不需要删 `.db`，旧数据完整保留
- **修改已有表**（加字段、改约束）：`IF NOT EXISTS` 不会更新已存在的表结构，早期无数据可删 `.db` 重建；有数据则用 `ALTER TABLE`（见下）

## JavaScript 对象语法：逗号规则

```javascript
const obj = {
  method1() { ... },   // ← 后面还有方法，加逗号
  method2() { ... },   // ← 后面还有方法，加逗号
  method3() { ... }    // ← 最后一个，不加逗号
};
```

对象字面量中，每个成员之间用逗号分隔。最后一个后面不加逗号（虽然 ES5+ 允许加，但不加更清晰）。忘记逗号会导致 `SyntaxError: Unexpected identifier`。

## 扫雷游戏（纯前端 + 后端排行榜）

**技术架构：**

| 层 | 在哪 | 干什么 |
|---|---|---|
| 棋盘渲染 | div 格子 + CSS | DOM 操作，不依赖 Canvas |
| 游戏逻辑 | `<script>` 标签内 | 布雷、翻开、标旗、胜负判定 |
| 成绩提交 | fetch → POST /api/minesweeper/save | JSON 通信 |
| 排行榜 | fetch → GET /api/minesweeper/leaderboard | JSON 返回，前端渲染 |

**关键技术点：**

- **首次点击才布雷**：避免玩家第一步就踩雷。在第一次点击时生成雷的位置，排除点击格及其周围 8 格，保证开局安全
- **Flood Fill（递归展开）**：点开一个周围无雷的空格后，自动递归展开相邻格，直到遇到数字边界。这是扫雷最核心的算法
- **事件委托**：不在每个格子上单独绑定事件，而是在父容器上监听 click 和 contextmenu，通过 `event.target` 判断点了哪个格子。性能好、代码少
- **右键标旗**：监听 `contextmenu` 事件，`event.preventDefault()` 阻止浏览器默认右键菜单
- **express.json()**：和 `express.urlencoded()` 是两件事。前者解析 JSON 请求体（`{ difficulty, time_seconds }`），后者解析表单（`title=LOL&content=xxx`）。两者互不干扰

**难度白名单校验：**

```javascript
const ALLOWED = ['beginner', 'intermediate', 'expert'];
if (!ALLOWED.includes(req.body.difficulty)) return res.status(400).json({ error: '非法难度' });
```

所有用户输入都要校验——攻击者可以发任意数据，不能信任前端传过来的值。

## 页面复用：partials（header/footer）

多个页面共享的 HTML 片段抽成 `views/partials/header.ejs` 和 `footer.ejs`，用 `<%- include('partials/header', { title: '扫雷' }) %>` 引用。

- `<%-` 不转义 HTML（用于渲染片段）
- `<%=` 转义 HTML（用于输出纯文本）
- include 第二个参数是传给子模板的变量

这样改导航栏只改 header 一处，所有页面自动更新。

## 前端公共函数抽离（public/js/utils.js）

`escapeHtml`（转义 HTML 防 XSS）原本写死在扫雷模板里，聊天功能也要用，于是抽到 `public/js/utils.js`，各页面用 `<script src="/js/utils.js">` 引入。

- 复用：一处定义、多页引用，不用复制粘贴
- `public/` 下的文件浏览器可直接访问（靠 `express.static` 托管）

## 阅读统计与 ALTER TABLE（改已有表的正解）

阅读量功能要给 posts 表加 `view_count` 字段，但表已建好且有旧数据——`CREATE TABLE IF NOT EXISTS` 只建不改。解决办法：`ALTER TABLE ADD COLUMN`。

```javascript
db.run('ALTER TABLE posts ADD COLUMN view_count INTEGER DEFAULT 0', () => {});
```

- 空回调 `() => {}` 的作用：吞掉「列已存在」的报错。这样重复启动服务、或全新数据库（建表时已含该列）都不会崩。
- 这是「改已有表结构」的正确姿势：**不删库、不丢数据**。
- 阅读量在 `GET /posts/:id` 里 `view_count = view_count + 1`，每访问一次详情页自增一次。

## 聚合查询：SUM 与 COALESCE

全站阅读总量用聚合函数：

```sql
SELECT COALESCE(SUM(view_count), 0) AS total FROM posts
```

- `SUM()`：把某列所有行相加
- `COALESCE(a, b)`：a 为 NULL 时取 b。空表时 `SUM` 返回 NULL，用 COALESCE 兜底成 0，避免前端显示 null

## 对话闲人：集成外部 AI API（Agent 功能）

调 DeepSeek 的 `chat/completions` 接口，给博客加一个 AI 聊天角色。核心链路：

```
浏览器 fetch /api/chat → 你的服务器 chatService → fetch DeepSeek API → 返回 AI 回复
```

- **为什么要经过自己的服务器转发，不让浏览器直接调 DeepSeek？** 因为 API Key 不能暴露在前端（谁都能看网页源码）。Key 只存服务器 / 数据库。
- **人格靠 system prompt**：messages 数组第一条 `{ role: 'system', content: '你是闲人…' }` 定义说话风格，第二条 `{ role: 'user', content: 用户消息 }`。
- **Node 18+ 自带 `fetch`**：服务端也能直接用 fetch 调外部 API，不用装 axios。
- **额度机制**：users 表加 `free_chat_count`（免费次数）和 `own_api_key`（用户自己的 Key）。免费次数 > 0 用服务端 Key 并 -1；用完后用用户自己的 Key（不扣次数）；两者都没有则报错提示去设置页。

**API Key 安全三原则：**
1. 存服务器 / 数据库，绝不进前端
2. 设置页只回显后 4 位（`'••••' + key.slice(-4)`），不返回完整 Key
3. 服务端默认 Key 从环境变量读（`process.env.DEEPSEEK_API_KEY`），不硬编码、不进 git

## 接口限流：express-rate-limit

AI 接口、成绩提交这类「消耗资源」的接口要防刷：

```javascript
const chatLimiter = rateLimit({ windowMs: 60 * 1000, max: 20 });
app.post('/api/chat', chatLimiter, handler);
```

- 按 IP 计数，每分钟超过 max 次返回 `429`。
- 限流器是中间件，写在处理函数前面：`app.post(路径, 限流器, 处理函数)`——请求先过限流器，再进业务逻辑。
- 用途：防止有人一秒刷上千次，刷爆你的 API 额度或服务器。

## 反思

> **扫雷的游戏逻辑和博客 CRUD 是两种思维。** — 博客功能围绕着数据库增删改查，扫雷围绕着前端状态管理（棋盘数组、计时器、游戏状态）。这个差异恰好证明了"同原理功能堆砌"的反面——你在同一个项目里接触到了不同范式的问题。

> **"首次点击才布雷"不是多余的细节。** — 如果不做这个优化，玩家开局可能第一下直接踩雷，体验极差。用户体验往往藏在边界条件里，不写在需求文档上。

> **编辑功能 = 创建功能的复用 + 权限校验。** — `edit.ejs` 和 `write.ejs` 几乎一样，区别只是表单 action 指向了带 id 的路由、input/textarea 用 `value` 预填了原有数据。新知识只有"权限校验"这一点：后端要判断 `post.user_id === req.session.user.id`，保证只有作者能改。

> **为什么模板里做权限判断不够？** — `post.ejs` 里用 `<% if (user && user.id === post.user_id) { %>` 隐藏了编辑按钮，但这是前端防护。有人可以直接在地址栏输入 `/posts/3/edit` 绕过。后端路由里的权限校验才是真正的安全线。前端的隐藏只是改善体验（不让非作者看到没用的按钮）。

> **db 是什么？不是某个特定数据，是一条连接管道。** — `new sqlite3.Database(path)` 返回的不是数据本身，而是一个能操作数据库文件的对象。后面的 `db.run()`、`db.get()` 都是通过它来执行的。理解了这一点，"连接"和"数据"的区别就清楚了。

> **代码文件不是网页** — `app.js` 不能拖进浏览器。它是被 Node.js 执行后变成一个常驻服务，浏览器再去请求这个服务。代码 → 运行 → 服务 → 网页，这四个环节必须分清。

> **一个字段的改动要改三层。** — 注册流程去掉 email：建表语句 → Model（getByEmail + create 参数）→ Service（register 逻辑），漏一层就报错。另外，改完建表语句后旧 `.db` 文件不会自动更新（`CREATE TABLE IF NOT EXISTS` 只建不修），开发阶段直接删 `.db` 让它重建。

> **「改表必须删库」是阶段性结论，不是真理。** — 早期没数据时，删 `.db` 重建最省事；但一旦有真实用户数据，删库 = 毁数据。正确姿势是 `ALTER TABLE ADD COLUMN` + 空回调容错。同一个问题在不同阶段有不同最优解——这次开发中真的丢过一次数据，就是没分清这两个阶段。

> **AI 功能的关键不在「调通 API」，而在「Key 怎么藏」。** — 让浏览器直接调 DeepSeek，三行代码就够，但 Key 会暴露给所有人。加一层自己的服务器转发，本质就是为了守住 Key。很多「后端存在的意义」都是这种「前端做不了 / 做了不安全」的事。

> **额度设计体现的是产品思维，不是技术难度。** — 免费 10 次 + 用完让用户填自己的 Key：既控制了自己的成本，又不完全卡死用户。技术实现（两个字段 + 几个判断分支）不难，难的是想到这个「既省钱又留住用户」的规则。

> **EJS 分不清「代码」和「注释」。** — 它只是纯文本扫描 `<% %>`。我在 `<script>` 的 JS 注释里写了 `<%-`，直接把模板搞崩。模板引擎的本质是字符串替换，别指望它懂 JavaScript 语法。
